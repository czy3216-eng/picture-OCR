## paddle_ocr.py 多进程死锁 → 回退单进程
- **根因**: Windows 多进程 Pool，每个 worker 同时初始化 PaddleOCR → `Creating model` 阶段文件竞争死锁，卡死 10min+
- **修复**: 完全移除 multiprocessing，改回单进程顺序处理
- PaddleOCR 只初始化一次（主进程），逐张 OCR 处理 704 张
- 预计耗时: 3-5 分钟（单张 0.3-0.5s），可能达不到 60s 目标但稳定可用
- 加速参数保留: use_textline_orientation=False, det_limit_side_len=640, rec_batch_num=8

## paddle_ocr.py 重启→单进程卡模型加载→参数deprecated静默崩溃
- `PaddleOCR()` 构造函数卡在 `Creating model`，det_limit_side_len/rec_batch_num 已deprecated
- 模型加载完成后无任何结果输出，静默崩溃

## paddle_ocr.py 最终方案：放弃 PaddleOCR → 换 RapidOCR
- 文件名保持 `paddle_ocr.py` 不变，引擎从 `paddleocr.PaddleOCR` → `rapidocr_onnxruntime.RapidOCR`
- 优势：ONNX Runtime 秒启，不需要 paddlepaddle，稳定可靠
- ThreadPoolExecutor 多线程并发，预计 speed 接近 ocr_color.py（47s/704张）
- 输出格式路径不变：`D:/a-test/result/ocr_color_paddle_{timestamp}.json`

## ollama_ocr.py v4 — 性能最大化 (实测 10张=21s/张 全优化)
- **实测**: 8 workers × Docker Ollama → 10张/46s, 5/5 TIME, avg 21.78s
- **根因**: GPU 推理本质串行, worker 过多 → 排队拥塞 → TIME + HTTP500
- **v4 优化**:
  1. workers: 8→3 (匹配 Ollama GPU 并发能力)
  2. timeout: 30s→60s (VL 首次推理慢)
  3. 超时/500 自动重试 1 次 (间隔 2-3s)
  4. Prompt 极简: num_predict 20→16, 文本预热替代图片预热
  5. `--no-retry` 跳过重试
- Docker: `docker exec <容器名> ollama pull qwen3-vl:8b`
